Chlorine Genie — Display Selection Summary

Decision brief & criteria recap · companion to the bilingual sourcing RFQ

1. Overview

We're selecting the touchscreen display for the next hardware iteration of the Chlorine Genie. The current unit is a 7" smart serial display module that is robust but feels low-end, and its UI can only be updated by inserting an SD card into the module — unacceptable for fielded units. The goal is a premium-feeling 10.1" display with remote/OTA updatability, while keeping BOM cost reasonable.

The host MCU is an ESP32-S3, which stays as the system controller. Two solution tracks are being quoted in parallel so we can compare on cost and capability; the output of this effort is a bilingual (EN/中文) RFQ for the China sourcing team to find candidates.

2. What Makes a Display Feel "Premium" (criteria framework)

Spec What to target Why it matters
Optical bonding Full lamination (OCA/OCR); no air gap Single biggest "premium" lever — kills internal reflections, improves sunlight readability, contrast, ruggedness; the main reason the current panel feels cheap
Panel technology IPS (wide-view); avoid TN. OLED risks burn-in on static HMI Viewing-angle stability and color; TN reads as low-end
Resolution / pixel density Match PPI to viewing distance (≈150 PPI at arm's length) Angular resolution, not raw PPI, sets perceived sharpness; below threshold → visible pixels, cheap feel
Brightness / ambient contrast ≥1000 nits for sunlight; pair with AR coating Brightness alone doesn't help if reflections wash it out — ambient contrast is the real metric
Cover glass + coatings Chemically strengthened glass; AR + anti-fingerprint Surface feel and glare control are tactile/visual premium cues
Refresh + pixel response 60 Hz baseline (90/120 Hz feels premium); GtG ≤ ~10 ms Smooth scroll/animation; slow pixel response smears regardless of refresh
Touch latency / report rate End-to-end < ~50 ms; 120 Hz+ scan rate The dominant "feel" driver — perceptible far below intuition
Touch — water rejection PCAP with wet-finger / water-rejection mode Pool/splash environment; plain PCAP misfires when wet
Color depth / gamut 8-bit (16.7M); ≥70% sRGB Banding-free gradients, richer UI

4. Architecture: The Two Tracks

Current setup: a smart serial display module (DWIN/Nextion-class) — its own MCU + GPU, driven by high-level UART commands, UI stored as a compiled blob updated via SD card. The "cheap feel" traces to the panel (non-bonded), not the architecture itself.

Option A — Better bonded smart serial module. Keeps the current "S3 sends UART commands" model. Lower integration risk and faster bring-up since the module renders everything. Must use a bonded IPS panel and support serial UI download over the host UART (no SD-card-only path).

Option B — Bare MIPI-DSI panel + ESP32-P4 display co-processor. The S3 stays the system brain; a P4 handles rendering and drives a bonded DSI panel, linked over UART/SPI. Higher graphics ceiling and the cleanest OTA (UI lives in our firmware/asset pipeline). More firmware bring-up effort; P4 toolchain still maturing and needs a companion radio for wireless.

Why not drive the panel directly from the ESP32-S3? The S3's RGB interface is bandwidth-limited: ~800×480 @ 60 Hz is comfortable, 1024×600 is marginal (bounce buffers, tearing risk), and 1280×800 isn't viable. It also consumes ~20 GPIOs, which collides with the existing RS485/Modbus and sensor load. For a premium 10.1" at 1280×800, S3-native forces a quality compromise — ruled out.

A vs B — the real deciding factor: The choice comes down to firmware effort and OTA/UI control, not parts cost. Option A is faster to a premium result; Option B gives full UI ownership and cleaner OTA at the cost of P4 + LVGL bring-up.
